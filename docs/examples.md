# 三个合成示例

以下任务先明确范围与完成线，再使用原 Skill；不是性能实验，也不会自动开始执行。
交付默认写在本次任务内，不继承上一次的 push/PR 许可。

## 1. 小范围清理：一个 lane 足够

在自己复制的合成仓库中：

```text
/herdr-dispatch:dispatch-codex
仅清理这个实验分支里的旧开发 Agent 引导文件和已确认无引用的运行产物。
保留产品运行所需的 AI 提示词、工具与业务代码。先按用途列清理清单，
有不明确引用就保留并说明。一个 lane；复用现有目录调查。
验收：检查删除 diff、依赖引用和受影响启动检查。
完成后做一次本地提交，不 push、不开 PR；不要清理别的目录。
```

主管应区分开发辅助与产品 AI，独立核对删除范围；没有风险依据时不扩成全项目重构。
若出现新业务问题，记录后续事项，不把它偷偷加入清理验收。

## 2. 两个独立函数：用原生子 Agent 解决局部问题

仓库内 [demo](../demo/README.md) 提供未实现的两个 Python 函数和事先编写的验收测试。
按 [setup](setup.md) 把 demo 初始化为独立实验 Git 仓库后，在其 Herdr pane 里运行：

```text
/herdr-dispatch:dispatch-codex
完成 demo README 中的 slugify 与 summarize_numbers；保留既有测试。
两模块互不写同一文件，可最多两个 lane；worker 可按需要使用 Opus 原生子 Agent，
但每次委派须有独立问题和产物，不重复勘探已经提供的规范。
验收各自测试及最终组合测试。仅本地提交，由主管独立验收后报告，不 push、不开 PR。
```

一份 worktree 是一个代码目录；原生子 Agent 是 lane 内协作者，两者不是一回事。
若任务小到拆分成本更高，可以用一个 lane 顺序完成，不必凑满两个。
验收后保留分支和结果；清理 worktree 由用户另行决定。

## 3. 一次证据驱动的文档迭代

```text
仅复盘我指定 run 的摘要、子 Agent 关系、验收结果和必要日志片段。
检查是否重复调查、等待错误对象拍板、把正常长任务当停滞。
区分事实、推断和未知；最多提出三个候选，不启动额外观察 Agent。
选一个可检验的规则改动，保持验收和权限不变；实现前向我展示修改范围。
```

例如证据显示“通知已发出，但主管未收到”时，应先确认 run/session、目标 pane 和接收状态；
它不能直接证明需要高频模型巡检。修改候选应说明原假设、竞争解释、目标规则和回退版本。

采用候选后用同起点、同任务、同环境比较旧版与新版；保留单 Agent 基线及失败尝试，
同时看质量、总消耗、完成时延和人工介入。未完成对照只能记作假设。
测试通过才打新标签；下一次冷启动验证实际加载哈希。这里没有自动优化器。

## 同一任务，三个配置

新建草稿，把“补齐来件处理包”的业务需求和验收写一次。A 保持 Opus/max；B 用
Opus/medium；C 用 Fable/medium，并行设 2。也可以保留全部模型设置，只让 C 选择
你另一个 Git 分支上的四文档版本。一次改多个因素时，结论只适用于整套配置。

本地输入 `复制 A 为 D；D 用 Fable 5 medium；并行 2 组` 后核对界面差异。
冻结后每组独立分支、目录和会话；用 [服务配方](experiments.md)管理各组端口。
最终保留失败尝试和证据不足项，人工比较，再决定下一轮是否采用某个文档版本。
这是使用示例，不是模型优劣或效率提升的测试结论。
